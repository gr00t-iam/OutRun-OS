3. WHAT CHANGED IN 1.0 (since the v0.96-dev desktop milestone)
--------------------------------------------------------------

  apps/calc.c        Operator precedence: * and / bind tighter than + and -,
                     equal precedence left-to-right. Two-level pending stack
                     (lhs/op + low_lhs/low_op) — with two levels there is never
                     a third, so it is a complete stack. Deferred operations are
                     overflow/zero-divide checked when finally applied. The
                     "Pending:" line shows both operators ("+ *").
  apps/vault_pad.c   g/G document jumps. One-line clipboard: y yank, D cut,
                     p paste-below (1 KiB cap; an over-long line is REFUSED, not
                     truncated). Overwrite confirmation: save onto a file that
                     exists and is not this buffer's origin asks once; the next
                     save confirms; any other key withdraws. The existence probe
                     opens with flags 0 so it cannot create.
  apps/task_mgr.c    Click PID / CPU column headers to sort. Stable insertion
                     sort producing an index table over the kernel's list — the
                     list itself is never permuted, so monitor_sample's cross-
                     sample pid matching is untouched (asserted). Per-row CPU
                     share column. NO memory sort: outrun_process has no memory
                     field and a fabricated column is not a feature. Graphs
                     auto-scale to the observed peak with a floor of 20.
  apps/settings.c    Instant apply: a row click pushes to the kernel in the
                     same step; on refusal the local copy rolls back so the
                     screen never shows a value the desktop is not honouring.
                     APPLY button removed; RELOAD kept.
  kernel64.c         Desktop heartbeat prints frames_used= by the same
                     expression SYS_DESKTOP_INFO reports (needed so the soak
                     reads a counter something actually prints).
                     KERNEL_VERSION 1.0.0-metal.
  Makefile           VERSION 1.0.0. New: desktop-soak, gate-desktop.
                     release-iso builds + checksums BOTH images; release-verify
                     boots both.
  tools/             desktop-soak.py (new). desktop-ui-test.py: no-tearing
                     sample moved to the RELOAD button / REPEAT DELAY row since
                     a scale click now magnifies the pixels being sampled.
  docs/              CHANGELOG-1.0.0.md.

  9a. WHY A NEW SYSCALL RATHER THAN DRIVING THE SHELL
  ---------------------------------------------------

  The obvious way to build a disk manager on this system is to call
  SYS_RUN_CMD("cas") and parse the output, the way OUTRUN TERM does. That was
  rejected. `disk`, `cas` and `vfs` are SELF-TESTS: they write sectors, put
  blocks and create files. A monitor whose refresh mutates the volume it is
  monitoring is not a monitor, and a pool-usage figure that the act of reading
  it increased is not a measurement.

  So SYS_HW_INFO (119) was added: read-only, four domains, one struct each in
  include/outrun_abi.h.

      HW_STORAGE  CAS superblock, pool counters, journal recovery counters,
                  VFS directory occupancy, the block-device inventory
      HW_PCI      the device registry: BAR windows, required capability,
                  host-binding, ring-3 ownership, quiesce availability, and
                  config dwords 0x00/0x08/0x0C/0x34 read by the kernel
      HW_TRACE    per-core ring-3 busy time and excursion counts, per-line and
                  per-core interrupt counts, the frame allocator, the thread
                  table and the process table
      HW_NET      the interface's frame AND byte counters, its MAC and address,
                  and every live socket with its TCP state

  SYS_FB_CAPTURE (120) was added for the screenshot tool: it copies a rectangle
  of the composited LOGICAL desktop into the caller's buffer.

  Both calls follow case 117's contract exactly — PCAP_WIMP, access_ok before
  any write, and a SIZE THAT IS CHECKED rather than assumed, so a program built
  against a different revision of the header is refused instead of partly
  filled. Four _Static_asserts were added beside the kernel's local struct
  declarations pinning each domain's size (304 / 2704 / 2816 / 856 bytes). The
  runtime check catches a stale CALLER; the static one catches a stale KERNEL,
  which the runtime check could only ever have reported as every caller
  mysteriously receiving -EINVAL.

  NOTHING IN THESE STRUCTS IS A PLACEHOLDER. Three fields were designed and
  then removed because no live source existed for them, rather than shipped
  reading zero:

    - cpu_busy_ticks / cpu_idle_ticks, derived from the timer tick. The PIT
      interrupts the BSP, so every AP would have read zero on a machine plainly
      using all four cores. Replaced by cpu_busy_ns, accumulated at the site in
      resume_kernel that ALREADY charges the process — the one place a core
      knows both how long an excursion ran and that it ran there.
    - a mount table for the disk manager. This kernel's VFS is flat and has no
      mounts; the FILES tab derives directory prefixes from the names instead,
      and says so.
    - a link-configuration pane for the network deck. The stack's address and
      MTU are compile-time constants with no syscall to change them, so the app
      displays them and states on screen that it does not configure the link.
      A settings pane reading back a constant could never be wrong and could
      never do anything.

  Three counters DID have to be created, and each was created with its
  increment site at a chokepoint and a print site that emits it:

    - g_irq_line_count[16] and g_irq_cpu_count[16][MAX_CPUS], incremented in
      the interrupt dispatcher for every vector 32..47 — the timer and keyboard
      included, which the device-chain-only alternative would have left
      permanently zero on a machine plainly taking them.
    - g_cpu_busy_ns[] / g_cpu_excursions[], at the excursion fold above.
    - g_net_rx_frames and g_net_tx_bytes / g_net_rx_bytes. TX frames had been
      counted since v0.69 and RX had never been counted at all, so a network
      monitor could only ever have shown half a link. Bytes matter separately:
      sixty ARP frames and sixty full segments are the same frame count and two
      orders of magnitude apart.

  All of them are printed by `sched`, so a serial log can be checked against
  what the monitor displayed rather than the display being taken on its word.

  9b. THE APPLICATIONS
  ---------------------

  Every one was built test-first and every test was shown to be capable of
  failing — see 9c.

    apps/outrun_disks.c   DISK DECK.    CAS pool, block devices, VFS browser.
    apps/pci_view.c       PCI EXPLORE.  Bus inventory and the 0x34 capability
                          walk via SYS_PCI_CFG_READ on a claimed device.
    apps/sys_trace.c      SYS TRACE.    Per-core load, memory, IRQ
                          distribution, thread states.
    apps/net_deck.c       NET DECK.     Link, bandwidth, socket table.
    apps/outrun_snap.c    SNAPSHOT.     Desktop capture to a 24-bit BMP.
    apps/outrun_media.c   MEDIA.        Plays those BMPs into a paired window.
    apps/bmp.h            One codec, shared by the two above. A second copy in
                          the reader would be a second thing to keep correct
                          and the tests would only have covered one of them.

  Two design points worth recording because they were arrived at the hard way:

    - PCI EXPLORER CLAIMS AND RELEASES PER READ. SYS_PCI_CFG_READ serves only a
      device this process owns. Holding an exclusive claim for as long as a
      viewer window is open would make the tool a denial of service against
      every real driver that wanted the device. It is also the only tile
      granted PCAP_VFIO; the read-only inventory needs nothing but WIMP.
    - SNAP WRITES IN STRIPS. A 1024x768 capture is 3 MiB of pixels and 2.25 MiB
      of output; reserving that as BSS to take an occasional screenshot would
      cost it on every boot. The strip plan is asserted on the host to tile the
      rectangle EXACTLY for every height from 1 to 200 and every strip size
      from 1 to 70: overlap would duplicate rows and a gap would produce a file
      shorter than its own header claims — which is the truncation bmp_parse
      refuses.

  MEDIA's first blit called app_rect once per pixel. 129,000 clipped rectangle
  calls per frame, on a TCG-emulated machine, would have cost more per frame
  than the compositor spends on a hundred. It writes into the back surface
  directly; the bounds it skips re-checking are the ones media_fit establishes,
  and those are what the host tests assert for every size combination.

  9c. NEGATIVE CONTROLS
  ----------------------

  Per the standing rule that a test which cannot fail has not passed, each new
  test was run against a deliberately broken implementation:

    outrun_disks  truncation flag never set          -> caught (line 126)
    pci_view      capability loop reported as OK     -> caught (line 129)
    sys_trace     unsigned wrap instead of a floor   -> caught (line 99)
    net_deck      unsigned wrap instead of a floor   -> caught (line 57)
    outrun_media  frame timing catches up on a stall -> caught (line 93)
    bmp.h         truncation length check removed    -> caught (snap line 106)

  Two of these found real defects in the tests themselves rather than in the
  code, and both are recorded because the failure mode is subtle:

    - net_deck's first control did NOT fire. net_rate's overflow guard halved
      both terms until the product fitted, which drove the interval to zero for
      a large enough delta and then returned 0 — turning an absurd input into
      "no traffic", the one answer indistinguishable from a quiet link. The
      guard was replaced with a divide-first branch and the primitive is now
      asserted directly, because the sampled path cannot discriminate: a
      backwards counter produces a near-2^64 delta and every plausible rate
      calculation on a number that size lands back near zero somehow.
    - outrun_media's first control did not fire either. With three frames, a
      stall of 49 periods lands on the same frame whether the player advances
      by one or catches up. The stall lengths in the test are now chosen so the
      two policies disagree (3 periods and 9 periods).

  9d. THINGS THAT WERE ALREADY BROKEN AND ARE NOW NOT
  ----------------------------------------------------

    - MAX_BOOT_MODULES was 8. The desktop image now carries user_init plus
      TWELVE applications. Five modules would have been dropped SILENTLY:
      mod_find would simply not find them, five launcher tiles would have
      reported "no boot module" on an image that plainly contained them, and
      nothing in the build would have said why. Raised to 24, and the overflow
      now prints the name it dropped.
    - The launcher rail's tile height was the constant 44. Twelve tiles at 44px
      is 560 pixels; at scale 2 the logical desktop is 384 tall, so six tiles
      would have been drawn past the taskbar and been unclickable — which looks
      exactly like a launcher that ignores clicks. desk_tile_h() now derives
      the height from the space available and BOTH the compositor and the
      pointer call it, so the drawn tile and the hit box cannot disagree. At
      scale 1 it still evaluates to 44, which is why the existing UI test's
      hardcoded tile coordinates continue to hold.
    - pci_bdf_str masked the slot to four bits. Slot 0x1F is a real address and
      would have aliased onto slot 0x0F.

  9f. NOT COVERED (so "verified" stays "measured")
  -------------------------------------------------

  - The PCI capability WALK has not been exercised against a real device on
    this machine. Every enumerated function here is host-bound, and a device
    the kernel is driving is not claimable by design — so on a stock boot the
    walk reports its denial, which is correct behaviour and is what the app
    displays. The walk's loop, out-of-range, overflow and denial paths are

  10a. FOUR DEFECTS THE LIVE RUN FOUND, NONE VISIBLE TO A HOST TEST
  ------------------------------------------------------------------

  Every one of these was in code that passed its unit tests, and every one was
  found only by writing to a real filesystem.

  a. ONE WRITE PER ROW IS O(N^2). Writes on this VFS are not appends into an
     open extent — each one re-stores the file's WHOLE chunk map through the
     CAS. The first version issued one SYS_WRITE_FILE per row: 384 writes
     against a 450-chunk file. The first live boot spent ten minutes emitting
     the same four `put len 512` lines over and over and never finished. The
     image is now encoded whole and written in as few calls as the syscall
     allows.

  b. SYS_WRITE_FILE SILENTLY CLAMPS A SINGLE WRITE TO 64 KiB and returns the
     shorter count; it does not fail. So the one-call fix wrote an eighth of
     the image and reported success for that eighth. The write loops in 64 KiB
     chunks, and snap_chunk() is host-tested to tile any total exactly.

  c. THE FILE SIZE CEILING IS 256 KiB, NOT 2 MiB. The on-disk indirect map
     could address 2 MiB and the application's first guard was derived from
     the FORMAT — but VFS_MAX_FILE_BYTES caps a file at 512 chunks and it is
     the cap that decides. Deriving a limit from a structure rather than from
     the code that enforces it is how an application comes to believe a
     589,878-byte capture will fit.

     The consequence is worth recording plainly: on a 1024x768 desktop NO
     proportional region can be saved — a half-screen capture is 1.1 MiB. The
     CENTRE preset is therefore a FIXED 320x240 window, and it is the default,
     because a default the CAPTURE button would always refuse is not a
     default. The other three presets are refused, and the screen says TOO
     LARGE beside the byte count BEFORE the button is pressed.

  d. A SILENT APPLICATION CANNOT BE DEBUGGED FROM OUTSIDE. Two boots were
     spent unable to tell whether a click had missed its button, whether the
     region had been refused, or whether the write had failed — because the
     application's only account of itself was a status string on a surface.

11. PHASE 4 — STORAGE SCALING: THE WRITE COST AND THE FILE CEILING — 2026-09-09
-------------------------------------------------------------------------------

  Two bottlenecks section 10 found, fixed. Both were real; ONE OF THEM WAS NOT
  WHAT SECTION 10 SAID IT WAS, and that correction is the first thing here.

  11a. WHAT THE O(N^2) ACTUALLY WAS
  ----------------------------------

  Section 10 recorded, and the commit message for 3893a7f repeated, that "each
  write re-stores the file's whole chunk map through the CAS". That is WRONG,
  and reading vfs_write_at_locked rather than inferring from the log is what
  showed it. The kernel had already documented the true cause, in the function
  itself, since v0.84:

      THIS IS O(FILE), NOT O(WRITE) ... FNV-1a is sequential, so a byte changed
      in the middle invalidates every fold after it ... A file built by N
      sequential positional writes therefore costs O(N^2) in chunk reads.

  The chunk MAP was never the problem: chunks a write does not touch are reused
  by hash and never re-stored. What cost O(file) per write was recomputing
  file_hash — the content IDENTITY — by streaming every chunk of the file back
  out of the CAS through rust_cas_hash_cont. What I had seen in the log as
  repeated `put len 512` lines was the indirect-block rebuild, a much smaller
  term, and I attributed the whole cost to it without reading the code.

  THE FIX IS FOUR LINES, and it is exact rather than approximate. FNV-1a folds
  one byte at a time and rust_cas_hash_cont takes the running state as its
  seed — the property that function was written for. So when a write APPENDS
  ONTO A CHUNK BOUNDARY, the fold continues from the file's existing hash
  instead of restarting:

      if (oldlen && off == oldlen && (oldlen % 512) == 0) {
          from = oldnch;
          h = prev.file_hash;
      }

  Both preconditions are load-bearing and neither is a guess:

    off == oldlen       the write adds bytes and changes none, so every
                        existing chunk keeps its hash. The rebuild loop above
                        it PROVES this rather than assuming it — for i < oldnch,
                        cend <= off, so `overlaps` is false and the chunk is
                        reused by hash.
    oldlen % 512 == 0   the old file ended exactly on a chunk boundary, so its
                        last chunk was folded at its full 512 bytes. Without
                        this that chunk grows from partial to whole and its
                        contribution changes, which a continuation cannot see.

  oldlen == 0 deliberately takes the general path: file_hash is 0 for an empty
  file, not FNV1A_SEED, so there is no prefix state to resume.

  11b. THE CHECK, AND THAT IT CAN FAIL
  -------------------------------------

  `validate` now authors the same 3,584 bytes twice — once as a single
  whole-file write, once as seven sequential 512-byte appends — and asserts the
  two file_hashes are EQUAL. It asserts on the identity, not on a timing, so it
  cannot pass for the wrong reason on a fast host.

  NEGATIVE CONTROL, run before the real one: with the continuation seeded from
  FNV1A_SEED instead of the previous hash, the boot reported

      [valid  ]  PASS  VFS sequential appends all accepted
      [valid  ]  PASS  VFS append-built file has the whole-file length
      [valid  ]  FAIL  VFS incremental fold == whole-file fold
      [valid  ]  PASS  VFS append-built file reads back byte-exact

  which is exactly the shape that matters: the CONTENT was right and only the
  IDENTITY was wrong, so length and byte-exact read-back both passed and only
  the identity check caught it. A test suite without that assertion would have
  shipped a filesystem where one content had two identities depending on how it
  was written.

  11c. THE FILE CEILING: 256 KiB -> 2.5 MiB
  ------------------------------------------

  A full 1024x768 24-bit capture is 2,359,350 bytes = 4,610 chunks. The format
  reached 4,176 (16 direct + 64 single-indirect + 64*64 double-indirect), so the
  most obvious thing a desktop might want to store missed by 434 chunks.

  v1.2 adds ind3: a SECOND double-indirect block of the same shape as ind2,
  not a true triple-indirect. A third level would add another resolution path
  and 16 MiB of reach nothing here needs; a second D-block reuses the code that
  already exists and doubles the ceiling to 8,272 chunks (4.04 MiB).
  VFS_MAX_FILE_BYTES stops at 2.5 MiB because it also sizes two static
  chunk-hash arrays and the exec buffer.

  ITS HASH IS SPLIT ACROSS TWO NON-ADJACENT DIRENT FIELDS, and that is ugly on
  purpose. The dirent is exactly 256 bytes, every byte is on disk, and there
  were only two 4-byte holes left — _pad after nchunks and reserved[4] at the
  end — with no eight contiguous free bytes anywhere. Widening the dirent would
  break the on-disk directory layout, VFS_DIR_BLOCKS, the journal record and
  cas_mount's restore simultaneously and stop every existing volume mounting:
  a format break with a version bump and a reformat behind it, which is far
  more than a screenshot is worth. Both halves read ZERO on a volume written by
  any earlier kernel, and zero already means "this level is unused" for ind1
  and ind2 — the same compatibility rule v0.72 wrote for mode and v0.85 for the
  timestamps. Nothing open-codes the split: every read goes through
  vfs_ind3_get and every write through vfs_ind3_set.

  Two helpers were extracted so ind2 and ind3 cannot be handled differently by
  accident — vfs_build_dblock for construction and vfs_map_walk_dblock for the
  reference walk. A second copy of either is how a retain and a release drift
  apart and a live file's blocks get freed.

12. PHASE 5 — THE APPEND FAST PATH AND THE ind2/ind3 BOUNDARY — 2026-09-10
---------------------------------------------------------------------------

  Section 11f listed two gaps: nothing tested the ind2 -> ind3 transition, and
  the map rebuild was still not linear. Both are closed. The second one turned
  out to be a bigger and different problem than section 11 described, and the
  correction is again the first thing here.

  12a. MEASURED FIRST. THE COST WAS NOT WHERE SECTION 11 PUT IT
  --------------------------------------------------------------

  Section 11d named the remaining non-linear term as vfs_build_map_locked
  rebuilding the indirect blocks, "roughly 2,300 of those 7,667 puts". A
  benchmark was written before any optimisation — `vfsappend`, which builds a
  file by sequential 512-byte appends and reports the CAS operations of the
  LAST append against the FIRST. On the unmodified tree:

      built 256 chunks by sequential append in 6233 ticks (62330 ms)
      cas ops total: 1007 put, 133678 get
      first append: 1 put, 1 get
      last  append: 6 put, 1249 get
      per-write growth: last/first = 6.0x put, 1249.0x get

  Six puts. The indirect rebuild was never the expensive part. The cost was
  133,678 cas_GET calls, from three O(file) walks that ran on every write:

    1. the rebuild loop re-resolved every existing chunk through the indirect
       map (~2 cas_get each) only to hand the array to a builder that rewrote
       the same blocks;
    2. vfs_retain_map_locked walked all N chunks of the new map;
    3. vfs_release_map_locked walked all N of the old one.

  A claim about complexity that is made from reading code and not from counting
  operations is a guess. This one was wrong by two orders of magnitude in where
  the time went, and the counters are now permanent (g_cas_puts, g_cas_gets,
  incremented on every call in a shipping build and printed by `vfsappend`).

  12b. THE FIX: PATCH THE MAP, DO NOT REBUILD IT
  -----------------------------------------------

  vfs_append_locked handles a write that only ADDS bytes onto a chunk boundary
  and hands everything else back to the general path. It:

    - stores only the NEW chunks; nothing the file already had is read,
      resolved or re-stored;
    - PATCHES the map — a new chunk lands in the direct array, in ind1, or in
      one 64-entry group of ind2 or ind3, and only the blocks on that path are
      re-stored;
    - retains only the NEW chunks and the NEW indirect blocks, and releases
      only the REPLACED indirect blocks. Every chunk present in both maps would
      have been retained and then released, which cancels; doing neither is the
      same answer without the two O(file) walks.

  ORDER IS THE ROLLBACK ARGUMENT. Every cas_put happens before any cas_free.
  A release that ran first would return the old indirect blocks to the free
  pool, and a later failure would restore a dirent whose map points into
  reclaimed storage. The blocks to release are collected and freed only after
  the whole patch has succeeded.

  It DECLINES rather than improvises: an unaligned or non-appending write, a
  growth past the format, or a write touching more indirect groups than
  APPEND_MAX_OLD can hold all return 0 and fall through. A fast path that
  half-handles a case is worse than one that hands it back.

  12c. THE BENCHMARK, AFTER — AND A MEASUREMENT THAT COULD NOT FAIL
  ------------------------------------------------------------------

  The first "after" run reported numbers IDENTICAL to the before: 133,678 gets,
  1249x growth. Not a failed optimisation — a failed measurement. The benchmark
  called vfs_write_at_locked directly and so measured the general path on both
  sides of the change. That is the "test that cannot fail" this tree keeps
  warning about, aimed at an instrument instead of an assertion. There is now
  ONE dispatch, vfs_write_at_dispatch_locked, used by both the syscall path and
  the benchmark, so they cannot measure different things again.

  With the benchmark fixed, same 256-chunk workload, same host:

                          before        after       change
      wall time         62,330 ms    19,970 ms      3.1x faster
      cas_get total       133,678          666      200x fewer
      cas_put total         1,007          671      1.5x fewer
      last append     1,249 gets      3 gets        416x fewer
      growth last/first     1249x           3x      flat

  The 3x is a CONSTANT, not growth: the first append lands in the direct array
  (1 put, 1 get) while later ones patch one ind2 group (top + L1 get; L1, top
  and chunk put). It does not change with file size, which is what O(write)
  means. Wall time improves less than operations do because the remaining 20 s
  is dominated by one journal commit per append — 255 real dirent writes to
  disk — which is per-WRITE work and was never the quadratic term.

  12d. THE BOUNDARY TESTS
  ------------------------

  Twelve checks in `validate`, at exactly the transition: a file built to 4,176
  chunks must leave ind3 UNUSED and chunk 4,176 unresolvable; one more chunk
  must bring ind3 into use, resolve chunk 4,176 to the block written, leave
  chunk 4,175 resolving through ind2 UNCHANGED, and return nothing for 4,177.
  An off-by-one here does not corrupt loudly — it returns a hash of 0 for a
  chunk that exists, which reads as end-of-data, so the file would simply
  appear to stop at 2,138,112 bytes.

  The crossing chunk is given distinctive content so its hash cannot collide
  with the repeated filler, which is what makes "resolves to the right block"
  mean something.

  BUILT WITH THE FAST PATH, which is what makes it affordable at all: the
  general path costs 62 s for 256 chunks, so 4,176 chunks that way would have
  added many minutes to every tier of every gate run.

  AND THE FILE IS UNLINKED AGAIN — but that is NOT where the cost was, and the
  measurement says so. Three gate runs, same host:

      Phase 4, no boundary tests          465 / 400 / 430 / 440 s
      boundary tests, file left behind    630 / 565 / 595 / 600 s   (+165)
      boundary tests, file unlinked       605 / 550 / 570 / 580 s   (+140)

  So unlinking recovered ~25 s per tier, not the 165. The remaining ~140 s is
  the boundary file's CONSTRUCTION: 4,176 cas_put calls at roughly 33 ms each,
  because every put hashes 512 bytes and then searches the content index, which
  reads index blocks off the volume. The chunks all dedup to 64 real blocks —
  the volume is not storing 2 MB — but the put CALLS are unavoidable, because a
  4,176-chunk file is 4,176 chunks however cheaply each one stores.

  THAT IS A REAL AND PERMANENT TAX: about 9.3 minutes across a four-tier gate,
  on every run, forever. It is being paid deliberately, because this is the
  only test anywhere of the ind3 region and a test that is not in the gate is a
  test that does not run. It is recorded here rather than buried so that the
  next person can weigh it and reverse it if the trade stops being worth it.
  The unlink stays regardless: it is 25 s, and it exercises the release side of
  the boundary — the ind3 blocks have to come back, and the suite asserts that
  blocks were freed and that g_cas_ref_underflow is still zero.

  not one of my own assertions: the pre-existing `vfsstrs` suite passed with
  0 underflows and with its exact-baseline reclamation checks intact —

      cas-contend: allocated-but-unreferenced blocks return to EXACTLY their
      pre-soak value
      a full create-and-unlink cycle returns the unreferenced-block count to
      its EXACT pre-workload baseline

  Those compare derived reference counts against live ones. A fast path that
  retained or released one block too few would show up there before it showed
  up anywhere else.

  12f. NOT COVERED
  -----------------

  - The fast path is exercised at 512-byte and 32 KiB appends (validate,
    vfsappend) and at 64 KiB (the desktop capture). Appends wider than
    4 * VFS_IND_PER_BLK chunks are DECLINED by design and fall to the general
    path; nothing tests that they still produce the right file, beyond the
    general path's own pre-existing coverage.
  - Nothing tests the ind3 region FULL — a file of 8,272 chunks — because
    VFS_MAX_FILE_BYTES forbids it at 5,120.
  - The benchmark is one workload on one host, uniprocessor, with the volume
    warm. It is an instrument for comparing two builds, not a throughput
    figure for the filesystem.
  - No concurrent writer test: the fast path runs under g_vfs_lock exactly as
    the general path does, so the argument is the lock's, not a measurement's.

13. PHASE 6 — DEFERRED JOURNALLING AND THE MAP-PATCH RACE — 2026-09-10
----------------------------------------------------------------------

  13a. THE PREMISE WAS WRONG AGAIN, AND THE MEASUREMENT SAYS SO
  --------------------------------------------------------------

  Phase 6 was set up on the reading that the 19,970 ms remaining after Phase 5
  was "entirely bound by disk I/O from 256 synchronous journal commits". That
  was a reasonable inference — the CAS work had fallen to 666 gets and the
  journal was the obvious remaining suspect — and it is not what the numbers
  say. Deferred journalling was implemented, it works, and it cut journal disk
  writes by 16x:

      journal commits        256  ->   16
      journal disk blocks    512  ->   32
      wall time         19,970 ms  ->  18,700 ms      (6%)

  Sixteen times fewer synchronous disk writes bought six percent. So the
  journal was NOT the bottleneck either. What is left is the content itself:
  256 distinct 512-byte chunks, each a real virtio-blk write, plus the content
  index reads behind every cas_put. 128 KiB of new data under TCG is the floor,
  and the append path is now within a few percent of it.

  THIS IS THE THIRD PHASE RUNNING IN WHICH THE BOTTLENECK WAS SOMEWHERE OTHER
  THAN WHERE THE PLAN PUT IT. Phase 4 blamed the chunk map and it was the
  identity hash. Phase 5 blamed the indirect rebuild and it was the map walks.
  Phase 6 blamed the journal and it is the content writes. The counters added
  in Phase 5 (g_cas_puts / g_cas_gets) and here (journal commits and blocks)
  exist so the next such question is settled by reading a number.

  13b. WHAT DEFERRED JOURNALLING ACTUALLY CHANGES
  ------------------------------------------------

  A commit is two disk writes: the dirty directory block into its shadow slot,
  then the header that makes the transaction PENDING. Every append of one file
  dirties the SAME directory block, and only its last state is worth writing.
  vfs_journal_commit_lazy marks the dirent and returns having done no I/O; the
  writes happen at a flush point.

  FLUSH POINTS, and there is no background flusher:
    - SYS_VFS_SYNC, via vfs_journal_apply
    - SYS_CLOSE of any descriptor
    - VJ_LAZY_MAX (32) dirents pending
    - VJ_LAZY_TICKS (100 = 1 s) since the oldest became dirty, CHECKED ON THE
      NEXT APPEND. A deferred append with no VFS activity after it stays
      deferred until a sync or a close. Calling that a "timed flush" without
      this sentence would overstate it.
    - any EAGER commit, which stages the deferred dirents into its own
      transaction before publishing. Without that, a header naming only its own
      block would leave the directory current for one dirent and stale for
      another after a crash.

  In the 256-append benchmark all 16 flushes were epoch-forced: only one dirent
  was ever dirty, so the count threshold was never reached, and the file was
  built over ~18.7 s, which is ~16 one-second epochs. The mechanism and the
  arithmetic agree.

  WHAT IT COSTS A CRASH. An append that has not been flushed is lost, which is
  the POSIX bargain — data written without fsync may not survive a crash. What
  does NOT change is CONSISTENCY: content chunks reach the CAS before the
  dirent naming them is committed, so a dirent that reverts to an older length
  describes a shorter file and the chunks past its end are unreferenced and
  reclaimed. There is no state in which the directory names a chunk that is not
  there. ONLY the append fast path defers; whole-file writes, truncate, rename
  and unlink still commit eagerly, which is why the cross-reboot journal probe
  — which writes a file and halts WITHOUT syncing — still finds its transaction
  pending on the next boot.

  13c. THE CHECKS, AND THE CONTROL
  ---------------------------------

  Seven checks in `validate`. Two things have to be true and they pull in
  opposite directions: the appends must NOT each write the journal, or the
  optimisation does nothing; and after a flush the file must still be entirely
  there, or the optimisation lost data. Asserting only the first would pass for
  a filesystem that silently dropped writes. The disk-BLOCK counter is what
  makes the first half checkable — "deferred" means measurably fewer real
  virtio-blk writes, not a flag someone set.

  NEGATIVE CONTROL: with vfs_journal_commit_lazy routed straight to the eager
  commit, the boot reported

      FAIL  VFS deferring the appends wrote no journal blocks
      FAIL  VFS a flush is pending after the appends
      PASS  VFS the deferred file reads back byte-exact after the flush

  — the data checks still passing and only the deferral checks failing, which
  is the right discrimination.

  13d. THE MAP-PATCH RACE, AND TWO DEFECTS IT FOUND IN ITSELF
  ------------------------------------------------------------

  vfs_append_locked patches the map in place, so unlike the rebuild it replaced
  there ARE intermediate states in which the map is partly old and partly new.
  The only thing making them unobservable is that every reader and writer holds
  g_vfs_lock. `smprace` attacks that: four workers, two appending and two
  reading one file, with every reader verifying every chunk it can see against
  a pattern derived from the CHUNK INDEX — so any reader can check any chunk
  without knowing who wrote it.

  Result at -smp 4: 47 appends, 48 verified reads, 8/8 checks.

  IT FAILED TWICE FIRST, AND BOTH FAILURES WERE IN THE TEST:

  1. DRIVEN FROM THE AP IDLE LOOP IT DEADLOCKED THE BOOT. An AP took
     g_vfs_lock, issued a virtio-blk read, and waited for a completion it could
     not be woken for from that context — lock still held, every other core
     queued behind it. The boot managed one cas_put and then sat until the
     900 s harness timeout. cas_direct_burst runs in that context safely
     because it only touches the in-memory index and never blocks on the
     device; anything that can wait for the disk may not run there. Moved to
     BSP kernel threads, which is the vehicle the tree already uses for
     blocking VFS work (worker_fn), and which genuinely interleaves inside
     g_vfs_lock because klock tracks rank per THREAD precisely so a holder can
     park on a vblk wait.

  2. THE READER TOOK g_vfs_lock AND THEN CALLED vfs_read_file, WHICH TAKES IT
     TOO. A recursive acquisition of a rank-2 klock: the rank checker reported
     it and the readers made no progress. It was caught because the suite
     asserts the WORKLOAD HAPPENED before it asserts anything about the
     workload — 0 verified reads failed the first check rather than letting the
     other four pass vacuously on an empty run.

  13e. THE GATE CAUGHT A REGRESSION, AND IT WAS THE CLOSE FLUSH
  --------------------------------------------------------------

  The first gate run after this work FAILED. smp4-bios came back with 29
  failures — cas-contend, ofilestrs, appsstrs and posixstrs, every one of them
  a ring-3 worker missing its deadline or not reaching a terminal state. The
  other three tiers passed.

  Nothing was broken. Everything was QUEUED. SYS_CLOSE had been made to take
  g_vfs_lock unconditionally so a closed file would be durable, and almost
  every close has nothing deferred — so one of the hottest syscalls in the
  system had acquired a rank-2 lock it did not need, behind any thread holding
  that lock across disk I/O.

  The fix is to read g_vj_lazy_n WITHOUT the lock and take it only when there
  is something to publish. Being wrong is safe in exactly one direction and it
  is this one: a stale zero means this close skips a flush another core is
  arranging, and that core's own flush point — or the next close, sync or epoch
  — publishes it anyway. A stale non-zero costs one needless acquisition. The
  deferred set itself is only ever mutated under the lock.

  Worth recording as a shape, not just an incident: an optimisation whose whole
  purpose was to REMOVE disk writes from a hot path nearly shipped having ADDED
  a lock acquisition to a hotter one. The measurement that justified the change
  (journal blocks) was not the measurement that would have caught the cost.

  13g. NOT COVERED
  -----------------

  - NO CRASH TEST OF THE DEFERRED PATH. The consistency argument in 13b is from
    the code and the ordering, not from a power-cut experiment: nothing boots a
    volume whose last appends were deferred and unflushed. `cascrashwrite`
    exercises the EAGER path, which is unchanged. This is the largest gap here.
  - The race is BSP kernel threads, not two cores in the map at once. Since
    g_vfs_lock serialises map mutation by construction, what a two-core version
    would test is the lock rather than the patching — but that is an argument,
    not a measurement, and it is recorded as one.
  - The epoch is checked on the next append only. A single deferred append
    followed by silence stays unflushed until a sync or close; no test covers
    how long that window can be in practice.
  - The benchmark is one workload, one host, uniprocessor, warm volume. It
    compares two builds; it is not a throughput figure.
