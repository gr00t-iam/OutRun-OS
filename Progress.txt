3. WHAT CHANGED IN 1.0 (since the v0.96-dev desktop milestone)
--------------------------------------------------------------

  apps/calc.c        Operator precedence: * and / bind tighter than + and -,
                     equal precedence left-to-right. Two-level pending stack
                     (lhs/op + low_lhs/low_op) — with two levels there is never
                     a third, so it is a complete stack. Deferred operations are
                     overflow/zero-divide checked when finally applied. The
                     "Pending:" line shows both operators ("+ *").
  apps/vault_pad.c   g/G document jumps. One-line clipboard: y yank, D cut,
                     p paste-below (1 KiB cap; an over-long line is REFUSED, not
                     truncated). Overwrite confirmation: save onto a file that
                     exists and is not this buffer's origin asks once; the next
                     save confirms; any other key withdraws. The existence probe
                     opens with flags 0 so it cannot create.
  apps/task_mgr.c    Click PID / CPU column headers to sort. Stable insertion
                     sort producing an index table over the kernel's list — the
                     list itself is never permuted, so monitor_sample's cross-
                     sample pid matching is untouched (asserted). Per-row CPU
                     share column. NO memory sort: outrun_process has no memory
                     field and a fabricated column is not a feature. Graphs
                     auto-scale to the observed peak with a floor of 20.
  apps/settings.c    Instant apply: a row click pushes to the kernel in the
                     same step; on refusal the local copy rolls back so the
                     screen never shows a value the desktop is not honouring.
                     APPLY button removed; RELOAD kept.
  kernel64.c         Desktop heartbeat prints frames_used= by the same
                     expression SYS_DESKTOP_INFO reports (needed so the soak
                     reads a counter something actually prints).
                     KERNEL_VERSION 1.0.0-metal.
  Makefile           VERSION 1.0.0. New: desktop-soak, gate-desktop.
                     release-iso builds + checksums BOTH images; release-verify
                     boots both.
  tools/             desktop-soak.py (new). desktop-ui-test.py: no-tearing
                     sample moved to the RELOAD button / REPEAT DELAY row since
                     a scale click now magnifies the pixels being sampled.
  docs/              CHANGELOG-1.0.0.md.

  9a. WHY A NEW SYSCALL RATHER THAN DRIVING THE SHELL
  ---------------------------------------------------

  The obvious way to build a disk manager on this system is to call
  SYS_RUN_CMD("cas") and parse the output, the way OUTRUN TERM does. That was
  rejected. `disk`, `cas` and `vfs` are SELF-TESTS: they write sectors, put
  blocks and create files. A monitor whose refresh mutates the volume it is
  monitoring is not a monitor, and a pool-usage figure that the act of reading
  it increased is not a measurement.

  So SYS_HW_INFO (119) was added: read-only, four domains, one struct each in
  include/outrun_abi.h.

      HW_STORAGE  CAS superblock, pool counters, journal recovery counters,
                  VFS directory occupancy, the block-device inventory
      HW_PCI      the device registry: BAR windows, required capability,
                  host-binding, ring-3 ownership, quiesce availability, and
                  config dwords 0x00/0x08/0x0C/0x34 read by the kernel
      HW_TRACE    per-core ring-3 busy time and excursion counts, per-line and
                  per-core interrupt counts, the frame allocator, the thread
                  table and the process table
      HW_NET      the interface's frame AND byte counters, its MAC and address,
                  and every live socket with its TCP state

  SYS_FB_CAPTURE (120) was added for the screenshot tool: it copies a rectangle
  of the composited LOGICAL desktop into the caller's buffer.

  Both calls follow case 117's contract exactly — PCAP_WIMP, access_ok before
  any write, and a SIZE THAT IS CHECKED rather than assumed, so a program built
  against a different revision of the header is refused instead of partly
  filled. Four _Static_asserts were added beside the kernel's local struct
  declarations pinning each domain's size (304 / 2704 / 2816 / 856 bytes). The
  runtime check catches a stale CALLER; the static one catches a stale KERNEL,
  which the runtime check could only ever have reported as every caller
  mysteriously receiving -EINVAL.

  NOTHING IN THESE STRUCTS IS A PLACEHOLDER. Three fields were designed and
  then removed because no live source existed for them, rather than shipped
  reading zero:

    - cpu_busy_ticks / cpu_idle_ticks, derived from the timer tick. The PIT
      interrupts the BSP, so every AP would have read zero on a machine plainly
      using all four cores. Replaced by cpu_busy_ns, accumulated at the site in
      resume_kernel that ALREADY charges the process — the one place a core
      knows both how long an excursion ran and that it ran there.
    - a mount table for the disk manager. This kernel's VFS is flat and has no
      mounts; the FILES tab derives directory prefixes from the names instead,
      and says so.
    - a link-configuration pane for the network deck. The stack's address and
      MTU are compile-time constants with no syscall to change them, so the app
      displays them and states on screen that it does not configure the link.
      A settings pane reading back a constant could never be wrong and could
      never do anything.

  Three counters DID have to be created, and each was created with its
  increment site at a chokepoint and a print site that emits it:

    - g_irq_line_count[16] and g_irq_cpu_count[16][MAX_CPUS], incremented in
      the interrupt dispatcher for every vector 32..47 — the timer and keyboard
      included, which the device-chain-only alternative would have left
      permanently zero on a machine plainly taking them.
    - g_cpu_busy_ns[] / g_cpu_excursions[], at the excursion fold above.
    - g_net_rx_frames and g_net_tx_bytes / g_net_rx_bytes. TX frames had been
      counted since v0.69 and RX had never been counted at all, so a network
      monitor could only ever have shown half a link. Bytes matter separately:
      sixty ARP frames and sixty full segments are the same frame count and two
      orders of magnitude apart.

  All of them are printed by `sched`, so a serial log can be checked against
  what the monitor displayed rather than the display being taken on its word.

  9b. THE APPLICATIONS
  ---------------------

  Every one was built test-first and every test was shown to be capable of
  failing — see 9c.

    apps/outrun_disks.c   DISK DECK.    CAS pool, block devices, VFS browser.
    apps/pci_view.c       PCI EXPLORE.  Bus inventory and the 0x34 capability
                          walk via SYS_PCI_CFG_READ on a claimed device.
    apps/sys_trace.c      SYS TRACE.    Per-core load, memory, IRQ
                          distribution, thread states.
    apps/net_deck.c       NET DECK.     Link, bandwidth, socket table.
    apps/outrun_snap.c    SNAPSHOT.     Desktop capture to a 24-bit BMP.
    apps/outrun_media.c   MEDIA.        Plays those BMPs into a paired window.
    apps/bmp.h            One codec, shared by the two above. A second copy in
                          the reader would be a second thing to keep correct
                          and the tests would only have covered one of them.

  Two design points worth recording because they were arrived at the hard way:

    - PCI EXPLORER CLAIMS AND RELEASES PER READ. SYS_PCI_CFG_READ serves only a
      device this process owns. Holding an exclusive claim for as long as a
      viewer window is open would make the tool a denial of service against
      every real driver that wanted the device. It is also the only tile
      granted PCAP_VFIO; the read-only inventory needs nothing but WIMP.
    - SNAP WRITES IN STRIPS. A 1024x768 capture is 3 MiB of pixels and 2.25 MiB
      of output; reserving that as BSS to take an occasional screenshot would
      cost it on every boot. The strip plan is asserted on the host to tile the
      rectangle EXACTLY for every height from 1 to 200 and every strip size
      from 1 to 70: overlap would duplicate rows and a gap would produce a file
      shorter than its own header claims — which is the truncation bmp_parse
      refuses.

  MEDIA's first blit called app_rect once per pixel. 129,000 clipped rectangle
  calls per frame, on a TCG-emulated machine, would have cost more per frame
  than the compositor spends on a hundred. It writes into the back surface
  directly; the bounds it skips re-checking are the ones media_fit establishes,
  and those are what the host tests assert for every size combination.

  9c. NEGATIVE CONTROLS
  ----------------------

  Per the standing rule that a test which cannot fail has not passed, each new
  test was run against a deliberately broken implementation:

    outrun_disks  truncation flag never set          -> caught (line 126)
    pci_view      capability loop reported as OK     -> caught (line 129)
    sys_trace     unsigned wrap instead of a floor   -> caught (line 99)
    net_deck      unsigned wrap instead of a floor   -> caught (line 57)
    outrun_media  frame timing catches up on a stall -> caught (line 93)
    bmp.h         truncation length check removed    -> caught (snap line 106)

  Two of these found real defects in the tests themselves rather than in the
  code, and both are recorded because the failure mode is subtle:

    - net_deck's first control did NOT fire. net_rate's overflow guard halved
      both terms until the product fitted, which drove the interval to zero for
      a large enough delta and then returned 0 — turning an absurd input into
      "no traffic", the one answer indistinguishable from a quiet link. The
      guard was replaced with a divide-first branch and the primitive is now
      asserted directly, because the sampled path cannot discriminate: a
      backwards counter produces a near-2^64 delta and every plausible rate
      calculation on a number that size lands back near zero somehow.
    - outrun_media's first control did not fire either. With three frames, a
      stall of 49 periods lands on the same frame whether the player advances
      by one or catches up. The stall lengths in the test are now chosen so the
      two policies disagree (3 periods and 9 periods).

  9d. THINGS THAT WERE ALREADY BROKEN AND ARE NOW NOT
  ----------------------------------------------------

    - MAX_BOOT_MODULES was 8. The desktop image now carries user_init plus
      TWELVE applications. Five modules would have been dropped SILENTLY:
      mod_find would simply not find them, five launcher tiles would have
      reported "no boot module" on an image that plainly contained them, and
      nothing in the build would have said why. Raised to 24, and the overflow
      now prints the name it dropped.
    - The launcher rail's tile height was the constant 44. Twelve tiles at 44px
      is 560 pixels; at scale 2 the logical desktop is 384 tall, so six tiles
      would have been drawn past the taskbar and been unclickable — which looks
      exactly like a launcher that ignores clicks. desk_tile_h() now derives
      the height from the space available and BOTH the compositor and the
      pointer call it, so the drawn tile and the hit box cannot disagree. At
      scale 1 it still evaluates to 44, which is why the existing UI test's
      hardcoded tile coordinates continue to hold.
    - pci_bdf_str masked the slot to four bits. Slot 0x1F is a real address and
      would have aliased onto slot 0x0F.

  9f. NOT COVERED (so "verified" stays "measured")
  -------------------------------------------------

  - The PCI capability WALK has not been exercised against a real device on
    this machine. Every enumerated function here is host-bound, and a device
    the kernel is driving is not claimable by design — so on a stock boot the
    walk reports its denial, which is correct behaviour and is what the app
    displays. The walk's loop, out-of-range, overflow and denial paths are

  - Per-core load was observed on a uniprocessor desktop run. desktop-test-smp

  - One desktop boot per configuration. It cannot see an intermittent below

10. THE SNAP -> VFS -> MEDIA LOOP, ON A LIVE VOLUME — 2026-09-08
----------------------------------------------------------------

  (Section 9g by intent; numbered 10 because it is its own milestone.)

  §9f recorded that OUTRUN SNAP had never written a file and OUTRUN MEDIA had
  only ever been watched rendering an empty playlist. Both halves were covered
  by host tests; neither had been joined to the other on real storage. The
  reason was structural rather than an oversight: EVERY desktop target in this
  tree boots with no block device, so the desktop session had no volume to
  write to at all.

  `make desktop-media-test` (tools/desktop-media-test.py) attaches a virtio-blk
  volume to the desktop image and drives the whole loop through the real input
  path. 24/24 checks, image md5 6635d69968431b34aa2c30e7fe3855cb.

  THE EVIDENCE COMES FROM THREE INDEPENDENT PLACES, deliberately, because a
  screenshot alone cannot distinguish "it worked" from "it painted something":

    1. THE APPLICATION'S OWN WORDS, on the serial console. Both programs now
       announce every attempt through SYS_WRITE:

         [snap   ] capture 320x240@352,264 230454 bytes: SAVED
         [media  ] snap0000.bmp 320x240 DECODED

    2. THE GUEST'S OWN DIRECTORY. OUTRUN TERM ran the real `vfs` shell command,
       whose output kputc tees to serial, and the kernel listed the file in its
       own words:

         snap0000.bmp  (230454 bytes, 451 chunks, hash 1081bbe15813e7a8)

       230,454 is exactly 54 + 960*240: a 320x240 24-bit BMP to the byte.

    3. THE VOLUME, read by the HOST after shutdown. A block on vblk.img begins
       'BM' (0x4D42) and its little-endian size dword reads 230454 — the magic
       checked against the bytes actually on the disk, and tied to THIS file
       rather than to any BMP-shaped data by requiring the size to match what
       the directory reported. One matching block, one BM-like block.

  And the frame reached the screen: with the player relaunched, 95% of its
  video area changed against the same window's empty-playlist screenshot.

  10a. FOUR DEFECTS THE LIVE RUN FOUND, NONE VISIBLE TO A HOST TEST
  ------------------------------------------------------------------

  Every one of these was in code that passed its unit tests, and every one was
  found only by writing to a real filesystem.

  a. ONE WRITE PER ROW IS O(N^2). Writes on this VFS are not appends into an
     open extent — each one re-stores the file's WHOLE chunk map through the
     CAS. The first version issued one SYS_WRITE_FILE per row: 384 writes
     against a 450-chunk file. The first live boot spent ten minutes emitting
     the same four `put len 512` lines over and over and never finished. The
     image is now encoded whole and written in as few calls as the syscall
     allows.

  b. SYS_WRITE_FILE SILENTLY CLAMPS A SINGLE WRITE TO 64 KiB and returns the
     shorter count; it does not fail. So the one-call fix wrote an eighth of
     the image and reported success for that eighth. The write loops in 64 KiB
     chunks, and snap_chunk() is host-tested to tile any total exactly.

  c. THE FILE SIZE CEILING IS 256 KiB, NOT 2 MiB. The on-disk indirect map
     could address 2 MiB and the application's first guard was derived from
     the FORMAT — but VFS_MAX_FILE_BYTES caps a file at 512 chunks and it is
     the cap that decides. Deriving a limit from a structure rather than from
     the code that enforces it is how an application comes to believe a
     589,878-byte capture will fit.

     The consequence is worth recording plainly: on a 1024x768 desktop NO
     proportional region can be saved — a half-screen capture is 1.1 MiB. The
     CENTRE preset is therefore a FIXED 320x240 window, and it is the default,
     because a default the CAPTURE button would always refuse is not a
     default. The other three presets are refused, and the screen says TOO
     LARGE beside the byte count BEFORE the button is pressed.

  d. A SILENT APPLICATION CANNOT BE DEBUGGED FROM OUTSIDE. Two boots were
     spent unable to tell whether a click had missed its button, whether the
     region had been refused, or whether the write had failed — because the
     application's only account of itself was a status string on a surface.
     The SYS_WRITE lines in (1) above were added for that reason and are the
     thing that diagnosed (b) and (c) in one boot each.

  10b. THREE DEFECTS IN THE HARNESS ITSELF
  -----------------------------------------

  Recorded because a test that fails for its own reasons is worse than no test:
  it spends real boots and teaches nothing.

  - THE CLOSE BOX DEPENDS ON THE WINDOW'S WIDTH. The harness assumed 430 for
    every application; OUTRUN TERM is 600 wide, so its close click landed in
    content, the terminal stayed open, the player opened in window slot 2, and
    every subsequent screen sample looked at the wrong rectangle. Three checks
    failed downstream of one wrong constant.
  - A "WAIT UNTIL THE LOG GOES QUIET" HELPER CAN NEVER FIRE HERE. The desktop
    heartbeat prints forever. Completion is now taken from the application's
    own SAVED and DECODED lines, which are printed once and only after the
    work they describe.
  - A DISTINCT-COLOUR THRESHOLD WAS A GUESS, AND A WRONG ONE. A correctly
    decoded frame scored 11 colours against an invented floor of 32, because
    the captured region is mostly flat desktop. Replaced by a pixel difference
    against the same window's empty state, which needs no constant: 95%.

  10c. NOT COVERED BY THIS RUN
  -----------------------------

  - One capture, of one region, at one size. Multi-frame playback — the
    playlist ordering and frame advance that media_tick implements — is host-
    tested but has never been driven on a volume holding more than one .bmp.
  - The volume scan finds the header block; it does not reassemble the file
    from the CAS index and compare all 230,454 bytes against the framebuffer.
    Doing so would mean reimplementing the filesystem inside the test, which
    is verifying a system against a second copy of itself.
  - Uniprocessor only. This test has not been run at -smp 4.
  - The 16 MiB volume is far larger than the gate's 4 MiB. Behaviour when the
    volume is nearly full is not covered, and snap's "VOLUME FULL?" branch has
    therefore still never been taken.
